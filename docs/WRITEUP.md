# PostgreSQL expansion optimization — local research writeup

This is a local draft, not a submitted Kaggle Writeup or an official score.
The active competition is `python-postgre-sql-data-pipeline-optimization-challenge`.
No public Git remote has been configured; the exact public submission commit
is therefore not yet available. Code, pinned sources, reproduction commands,
negative results and raw reports are retained in this repository.

## Problem and bottlenecks

The unchanged organizer expands JSONB into six relational destinations, with
source/destination guards, counters, version dependencies and dump/replay
behavior. Repeated nested JSON extraction and 14-position table2 expansion
dominate PostgreSQL execution. In our 1M baseline, table2 took 111.518s and
table1 83.304s out of 270.084s of diagnostic SQL stages. Connection/transit
micro-optimization is not the priority for the official timing contract.

## Starting from the public implementation

The public control is QueryFoundry's exact submitted recipe source at
`32c283f32fe35e9b5bd0e538bd6631f305863fb3`. Its original module is retained
unchanged under `vendor/` with its license and SHA-256. qf_lazy calls that source
directly; qf_lazy_path1 replaces only its table1 extraction with our path
candidate. Early independent reproduction remains historical evidence, not a
substitute for the direct-source control.

We also measured all-TEXT jsonb_to_record projections, per-row payload/field
barriers, eager array expansion, direct #>> paths and a safe-domain fast-path
gate. Expensive gate validation was rejected rather than hidden outside timing.
The official function guard rejects jsonb_to_record's STABLE volatility; its
laboratory-only experiment does not weaken production validation.

## Measurements and correctness

Python 3.11.9, PostgreSQL 17.11 EDB on Windows 11, i7-12700H, 16 GiB RAM,
NVMe SSD; work_mem 4 MiB, shared_buffers 128 MiB, durability enabled. JIT is
unavailable in this binary. Sources were generated by the untouched official
fixed-seed generator at 100k and 1M rows.

The initial three-round 100k control reproduced a 22.74% diagnostic reduction
for lazy extraction. A later series showed substantial host drift, so that
percentage is not a stable final performance claim. Diagnostic reference-table
autovacuum was identified as an observer interference source and disabled;
normal source/destination maintenance was preserved. See EXPERIMENTS.md and
the individual reports for both successful and conflicting observations.

The completed 1M pilot, one run per variant:

| SQL path | Diagnostic seconds | Reduction vs same-run baseline |
|---|---:|---:|
| original baseline | 270.084 | — |
| direct QueryFoundry lazy_keys | 215.621 | 20.16% |
| table1 path + eager table2 arrays | 254.950 | 5.60% |

All six outputs passed bidirectional EXCEPT ALL at 1M, with surrogate identities
resolved through source IDs and dimension values. Counts, two typed hash sums,
schema/index/constraint checks and relationship checks also passed. This is
SQL diagnosis, not MEASURED PROCESSING TOTAL: complete preflight, managed
counters, version/dump handling, locks, commit latency and GUI/SSH are excluded
from the SQL-stage sum. Commit latency is reported separately.

Malformed-input testing prevents promoting an invalid fast path. More than
3,000 cases per conservative combined mode showed no observed difference;
direct QueryFoundry lazy modes still had SQLSTATE and acceptance/rejection
counterexamples. Independent payload/record barriers also admitted one input
rejected by baseline. The default launcher therefore remains baseline. These
results do not establish a new fastest valid submission.

Backend RSS samples during 1M DML were approximately 246–256 MiB; they include
shared mappings and do not measure whole-server peaks. Application RSS, WAL
cluster deltas and cumulative temp statistics are recorded. Cumulative temp
statistics include oracle activity and must not be presented as per-candidate
intermediate storage. Standalone EXPLAIN ANALYZE plans provide statement-level
buffer/WAL/temp evidence separately from uninstrumented timing.

## Durable recovery architecture

The new prototype builds dimensions once, then processes ordered raw-ID chunks.
Each chunk's four dependent inserts, original counters and checkpoint commit in
one logged transaction. Explicit main-row range predicates bound dependent
lookups as table1 grows. A persistent verified write fence protects source and
partial destinations across disconnected clients. Request SHA-256 binds job,
recipes, source versions, scope, actor and chunk size; actual source JSON and
metadata are fingerprinted rather than trusting stored raw_hash.

After data completion, the unchanged organizer version/dependency statements
and an audited receipt commit together in the separate control database. A
retry in the two-database gap resumes finalization. A final data commit removes
the fence and marks the job complete. This is an explicit saga, not distributed
atomic commit. Readers must honor job state while partial chunks are visible.

Twelve interruption boundaries passed on real PostgreSQL, including killed
backend/client, chunk commit boundaries and lost finalization responses. Tests
compare exact outputs, counters, chunk completion timestamps and six version
records. Source edits preserving raw_hash, same-count destination edits, schema
changes and version-dependency changes were rejected. Additional crash/dump
and full-cost prototype reports are kept separately when executed; no power-loss
or Linux/SSH equivalence is claimed.

The prototype supports initially empty destinations and positive raw IDs. It
does not yet provide automatic cancellation/undo, atomic publication to arbitrary
readers, or a default GUI resume flow. Fresh completion rehashes source three
times; the overhead must be assessed against recovery benefits. At 300M rows
the algorithm uses bounded chunk memory and small checkpoint metadata, but no
300M measurement or extrapolated winning score is claimed.

## Reproduction and remaining gates

recovery commands. app/ preserves all 32 organizer files. A clean source archive
